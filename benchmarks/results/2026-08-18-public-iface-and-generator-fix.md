# Прогон на публичном интерфейсе + исправление генератора — 2026-08-18

Продолжение сессии на том же стенде (2× Scaleway EM-I220E, EPYC 8124P 16c,
Ubuntu 24.04 / 6.8, Broadcom `bnxt_en` 25G, native XDP).
Предыдущий отчёт: `2026-08-18-scaleway-em-i220e.md`.

> **Важно.** Этот прогон выявил методическую ошибку в предыдущем отчёте.
> Вывод «фабрика Scaleway полисит ~940 kpps» **неверен** — см. раздел
> «Исправление». Сравнительные выводы про XDP/netfilter при этом устояли
> и подтвердились на нагрузке втрое выше.

## 1. Главная находка: pktgen отправлял всё в одну TX-очередь

Свип по числу потоков дал невозможную для «нормального» генератора кривую —
масштабирование сначала растёт, потом **падает**:

| потоков | pps (до фикса) |
|---:|---:|
| 1 | 665 928 |
| 2 | 1 172 619 |
| 3 | **1 490 218** ← пик |
| 4 | 1 483 740 |
| 5 | 1 015 164 |
| 6 | 931 570 |
| 8 | 938 293 |
| 12 | 882 449 |
| 16 | 817 517 |

Причина нашлась в `/proc/net/pktgen/eno12399np0@0`:

```
queue_map_min: 0  queue_map_max: 0
cur_queue_map: 0
```

Все потоки pktgen писали в **TX-очередь 0** и сериализовались на её спинлоке.
`bench_gen.sh` не выставлял `queue_map_*`, а дефолт — нулевая очередь.

### Фикс

В `configure()` каждому устройству `iface@N` прибивается своя очередь:

```bash
local qidx="${dev##*@}"
echo "queue_map_min $qidx" > "$PG/$dev"
echo "queue_map_max $qidx" > "$PG/$dev"
```

### Результат

| потоков | до | после | прирост |
|---:|---:|---:|---:|
| 4 | 1 483 740 | 2 680 646 | 1.8× |
| 8 | 938 293 | **5 004 812** | 5.3× |
| 16 | 817 517 | **5 237 245** | 6.4× |
| 24 | — | 4 866 477 | |
| 32 | — | 4 907 397 | |

Пик — **~5.24 Mpps на 16 потоках**. Спад после 16 объясним: у карты
8 combined-очередей, дальше потоки снова начинают делить их.

## 2. Исправление предыдущего отчёта

В прошлый раз все серии гонялись на `THREADS=8` — то есть **в провале
кривой**, на 18% от реальной возможности генератора. Отсюда неверная
атрибуция: потолок ~940 kpps был приписан полисеру Scaleway, хотя это
контенция очереди на самом генераторе.

Что есть на самом деле (замерено напрямую):

| Точка измерения | pps |
|---|---:|
| pktgen заявляет отправленным | 5 223 285 |
| **NIC генератора кладёт на провод** (`ip -s link` TX) | **4 960 912** |
| **DUT принимает, приватка (прямой L2)** | **2 130 899** |
| **DUT принимает, публичный путь (через роутер)** | ~1 840 000 |
| `rx_discards` на карте DUT за прогон | **0** |

Итог: **потолок фабрики существует, но он ~2.1 Mpps, а не 940 kpps**.
Генератор кладёт на провод 4.96 Mpps, карта DUT ничего не дропает
(discards = 0, `missed` растёт на ~900/с — мизер), CPU DUT простаивает.
Значит теряет именно сеть Scaleway, между машинами.

Публичный путь режет сильнее приватного (1.84 против 2.13 Mpps) — он идёт
через роутер: ARP на публичный IP DUT возвращает `c0:f8:7f:a9:46:47`,
не MAC самого сервера (`d4:04:e6:d9:44:80`). То есть proxy-ARP и
маршрутизация, а не L2-смежность.

## 3. Сравнение бэкендов на публичном интерфейсе

XDP уже висел на `eno12399np0` — этот интерфейс несёт и публичный трафик,
и VLAN приватной сети, так что переподнимать ничего не потребовалось.

### 3.1. Публичный путь, предложено 1.49 Mpps (4 потока)

| Бэкенд | Drop PPS | %soft (32 CPU) | %soft на 1 Mpps |
|---|---:|---:|---:|
| iptables | 1 410 353 | 10.02 | 7.11 |
| nftables | 1 497 442 | 10.87 | 7.26 |
| **eBPF/XDP** | **1 498 942** | **5.34** | **3.56** |

iptables при этой нагрузке **не справился**: обработал 1.41 Mpps против
1.50 у остальных двух.

### 3.2. Приватный путь, предложено 1.49 Mpps (4 потока)

| Бэкенд | Drop PPS | %soft | %soft на 1 Mpps |
|---|---:|---:|---:|
| iptables | 1 422 010 | 11.51 | 8.09 |
| nftables | 1 509 961 | 12.47 | 8.26 |
| **eBPF/XDP** | **1 515 364** | **5.88** | **3.88** |

Приватный путь стоит на ~13% дороже по CPU при той же нагрузке — цена
разбора VLAN-тега 3437 на каждом кадре.

### 3.3. Публичный путь, предложено 5.2 Mpps (16 потоков)

Доставлено фабрикой ~1.84 Mpps.

| Бэкенд | Drop PPS | %soft | %soft на 1 Mpps |
|---|---:|---:|---:|
| iptables | 1 756 361 | 12.19 | 6.94 |
| nftables | 1 840 438 | 13.29 | 7.22 |
| **eBPF/XDP** | **1 841 394** | **6.51** | **3.54** |

### 3.4. Сводка: во сколько раз XDP дешевле

| Сценарий | vs iptables | vs nftables |
|---|---:|---:|
| Публичный, 1.49 Mpps | 2.00× | 2.04× |
| Приватный, 1.49 Mpps | 2.09× | 2.13× |
| Публичный, 5.2 Mpps | 1.96× | 2.04× |
| *(старый отчёт, 0.94 Mpps)* | *2.03×* | *2.06×* |

**Отношение держится ~2× на всём диапазоне нагрузок** — от 0.94 до 1.84 Mpps
обработанных, на двух разных сетевых путях. Это делает вывод устойчивым:
он не артефакт конкретной нагрузки или пути.

## 4. Пояснения

**Почему XDP ровно вдвое, а не в 5–10 раз.** Выигрыш XDP — на пути, который
пакет не проходит: аллокация `sk_buff`, GRO, разбор L2/L3, route lookup,
и только потом хук netfilter. Но общая для всех часть — IRQ, NAPI-поллинг,
DMA, обвязка драйвера — остаётся. При 1.8 Mpps эта общая часть ещё весома,
поэтому разрыв держится около 2×. Он рос бы дальше с нагрузкой, но фабрика
Scaleway не даёт подняться выше ~2.1 Mpps.

**Почему iptables проигрывает в pps, а не только в CPU.** На 1.5 Mpps
iptables обработал 1.41 Mpps — начал терять. При линейном проходе цепочки
INPUT на каждый пакет стоимость фиксирована и на пике упирается в ядро,
обслуживающее очередь. nftables на одном правиле практически не отличается
от iptables по CPU (7.26 против 7.11 на Mpps) — его преимущество в наборах
правил (set/map lookup вместо линейного прохода), а не на единичном правиле.

**Что означает нулевой `rx_discards` при 57% потерь.** Пакеты не доходят до
карты DUT вообще. Это не переполнение кольца и не нехватка CPU — это отбор
в сети провайдера. Для бенчмарка дата-плейна это означает: на облачной
приватке абсолютный потолок XDP измерить нельзя, годятся только
сравнительные замеры при равной предложенной нагрузке.

## 4.5. Аудит sysctl: что было упущено

### Упущено и повлияло: `kernel.bpf_stats_enabled=1`

`bench_xdp.sh` **принудительно взводил** этот флаг при каждом запуске. Он
включает учёт `run_time_ns`/`run_cnt` для каждого исполнения BPF-программы —
то есть накладные ложатся ровно в измеряемый горячий путь XDP.

A/B с чередованием прогонов (16 потоков, ~1.84 Mpps):

| `bpf_stats_enabled` | drop pps | %soft |
|---:|---:|---:|
| 1 | 1 843 582 | 6.81 |
| 0 | 1 843 555 | **6.38** |
| 1 | 1 843 592 | 6.44 |
| 0 | 1 843 595 | **6.08** |
| **среднее 1** | | **6.63** |
| **среднее 0** | | **6.23** |

Цена — **0.4 п.п., то есть ~6% от всей стоимости XDP**. Пропускная способность
не меняется. Все предыдущие замеры XDP в обоих отчётах шли со включённой
статистикой, то есть **занижали преимущество XDP**.

Скорректированные отношения (публичный путь, 5.2 Mpps предложено):

| | %soft на 1 Mpps | vs XDP |
|---|---:|---:|
| iptables | 6.94 | **2.05×** |
| nftables | 7.22 | **2.14×** |
| eBPF/XDP (stats off) | 3.38 | 1× |

Исправлено: в `bench_xdp.sh` флаг вынесен в `BPF_STATS`, по умолчанию `0`.

### Проверено, оказалось в порядке

- **`nf_conntrack` не загружен.** Это была главная угроза честности сравнения:
  при загруженном conntrack каждый пакет проходил бы conntrack-lookup до
  правила DROP в filter/INPUT, и netfilter получил бы штраф, не относящийся
  к самому правилу. Модуля нет — сравнение чистое.
- `net.core.bpf_jit_enable=1`, `bpf_jit_harden=0` — верно (harden замедлил бы
  JIT-код XDP).
- `netdev_budget=60000`, `netdev_budget_usecs=4000`, `netdev_max_backlog=250000` — выставлены.
- `irqbalance` неактивен — привязка IRQ стабильна между прогонами.

### Проверено, не помогает

**Глубокие C-states** (`cpupower idle-set -D 0`): пропускная идентична
(1 840 703 против 1 840 463 pps), `%soft` даже выше — 7.07 против 6.32.
Это артефакт учёта (ядра не уходят в idle, меняется знаменатель), а не
реальная деградация. Применять смысла нет.

### Признано нерелевантным для этого пути

| sysctl | почему не влияет |
|---|---|
| `net.core.rmem_max`, `wmem_max`, `net.ipv4.udp_mem` | в измеряемом пути нет сокета — пакет умирает в XDP или в netfilter |
| `net.core.busy_poll`, `busy_read` | для чтения из сокета, не для softirq-обработки |
| `net.ipv4.conf.*.rp_filter` (=2, loose) | src-адреса настоящие, проверка тривиальна |
| `net.netfilter.nf_conntrack_*` | модуль не загружен |
| `tcp_*`, `somaxconn` | в нагрузке только UDP |
| GRO (`generic-receive-offload: on`) | XDP отрабатывает **до** GRO; влияет только на pass-путь |

`net.core.dev_weight=64` оставлен дефолтным — влияет на батчинг softirq,
эффект ожидаемо мал, отдельно не проверялся.

### Не sysctl, но потенциально важнее

Привязка RX-очередей к ядрам вручную не делалась — полагались на дефолт
драйвера (`irqbalance` выключен, поэтому affinity хотя бы стабильна между
прогонами). Для per-core замеров это следующий шаг: `ethtool -L combined N`
плюс явный пиннинг.

## 5. Изменения в коде по итогам

| Файл | Изменение | Статус |
|---|---|---|
| `benchmarks/bench_gen.sh` | `queue_map_min/max` по индексу потока — генератор ускорился в 6.4× | в рабочем дереве |
| `benchmarks/bench_gen.sh` | режим `PORTS_RND=1` (рандом портов при реальных IP) | в рабочем дереве |
| `init.sh` | `cargo +nightly` для сборки daemon/ctl | в рабочем дереве |
| `benchmarks/bench_xdp.sh` | `kernel.bpf_stats_enabled` вынесен в `BPF_STATS`, дефолт `0` — раньше скрипт сам портил свой замер | в рабочем дереве |

`queue_map` — самая ценная правка для разработчика: без неё любой бенчмарк
на этом харнессе меряет контенцию собственного генератора, а не дата-плейн.

## 6. Что осталось неизвестным

- **Природа потолка ~2.1 Mpps** не подтверждена вендором. В документации
  Scaleway pps-лимит для Private Networks не описан (документирован только
  ~100 kpps для Public Gateway, это другой продукт). Нужен тикет в саппорт.
- **Абсолютный потолок XDP** на этом железе не измерен — фабрика не даёт
  нагрузки, при которой дата-плейн начал бы захлёбываться. При 1.84 Mpps
  XDP тратил 6.5% CPU из 32 ядер, то есть запас кратный.
